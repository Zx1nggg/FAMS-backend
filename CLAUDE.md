## Project Overview

FAMS (Farm Aquaculture Management System) — a full-stack aquaculture management platform with JWT-based stateless authentication, RBAC, and multi-role data isolation (ADMIN / REGULATOR / FARMER).

**Backend (this directory):**
- **Java 21**, **Maven**, **Spring Boot 3.5.14**
- **MySQL** + **MyBatis-Plus 3.5.14** (ORM, code generator, logical delete)
- **Redis** (JWT token blacklist via jti)
- **Spring Security** + **jjwt 0.12.6** (HMAC-SHA signed tokens)
- **SpringDoc OpenAPI** (Swagger 3), **Lombok**, **FreeMarker** (code gen templates)

**Frontend (sibling directory `D:\华农\毕业设计\FAMS-Vue`):**
- **Vue 3** (Composition API + TypeScript), **Vite**, **Element Plus**, **Tailwind CSS v4**
- **Axios** (withCredentials), **Vue Router 5**, **ECharts**, **Pinia**

## Architecture

### Layered structure

Each business domain follows the same pattern, generated by MyBatis-Plus Generator:

```
modules/<domain>/
  entity/       — @TableName POJO extending Serializable
  mapper/       — extends BaseMapper<T> (+ optional XML in resources/mapper/)
  service/      — I*Service extends IService<T> / *ServiceImpl extends ServiceImpl<M, T>
  controller/   — @RestController, @RequestMapping("/modules.<domain>/<entity>")
```

### Module separation

- **`modules/system`** — Core RBAC: `User`, `Role`, `Menu`, `UserRole`, `RoleMenu`. Handcrafted, not generated.
- **`modules/temp`** — Generated business entities: `Farm`, `Pond`, `PondTask`, `HarvestRecord`, `IotSensorData`, `PurchaseBatch`, `Supplier`, `SeedlingDict`, `SopTemplate`, `AlarmRecord`, `BatchGrowthLog`, `PondFeedLog`. Controllers/services are stub skeletons waiting for business logic.

### Security flow

1. **Login**: `POST /api/auth/login` → `AuthController` authenticates via `AuthenticationManager` → `UserDetailsServiceImpl.loadUserByUsername()` → returns JWT with claims: `userId`, `username`, `userType`, `farmId`, `jti`.
2. **Token delivery**: JWT is written to both an `HttpOnly` cookie (`aqua_token`) and returned in the response body.
3. **Request filtering**: `JwtAuthenticationFilter` (a `OncePerRequestFilter`, registered before `UsernamePasswordAuthenticationFilter`) extracts the token from `Authorization: Bearer <token>` header or `aqua_token` cookie, validates it, checks Redis blacklist, then sets `SecurityContextHolder` and request attributes (`currentUserId`, `currentUserType`, `currentFarmId`).
4. **Second line**: `JwtAuthenticationInterceptor` checks that request attributes were set by the filter; throws `BusinessException(401)` if not.
5. **Logout**: `POST /api/auth/logout` adds the token's `jti` to a Redis blacklist with TTL matching remaining token validity, then clears the cookie.

### Data isolation

FARMER users have a `farmId` in their JWT claims, injected into request attributes. All FARMER-scoped queries should filter by this `farmId`. ADMIN and REGULATOR have `farmId=null` and see all data.

### Key conventions

- **API response**: Always use `Result<T>` (fields: `code`, `message`, `data`). Success via `Result.success(data)`, errors via `Result.error(code, msg)` or throw `BusinessException`.
- **Business exceptions**: Throw `BusinessException(code, message)` — caught by `GlobalExceptionHandler` and converted to `Result.error()`.
- **HTTP status**: Business errors return HTTP 200 with the error code in the JSON body (not HTTP 4xx/5xx), set in `SecurityConfig.exceptionHandling`.
- **MyBatis-Plus**: ID strategy is `auto`, logical delete field is `is_deleted` (1=deleted, 0=active), camelCase mapping enabled, SQL logging to stdout.
- **Password encoding**: `BCryptPasswordEncoder` (via `org.mindrot.jbcrypt`).

### Config files

- `application.yml` — DataSource, Redis, MyBatis-Plus, JWT settings
- `SecurityConfig.java` — Security filter chain, CORS, password encoder, auth entry points
- `WebMvcConfig.java` — Interceptor registration and CORS mappings

### Route structure

| Path | View | Auth required |
|---|---|---|
| `/` | `views/portal/Index.vue` — role selection portal | No |
| `/login?role=<type>` | `views/login/Login.vue` — login form | No |
| `/dashboard/farmer` | `views/dashboard/Farmer.vue` | Yes |
| `/dashboard/regulator` | `views/dashboard/Regulator.vue` | Yes |
| `/dashboard/admin` | (not yet implemented) | — |

The route guard in `router/index.ts` checks for `aqua_user` in `sessionStorage` before allowing access to `/dashboard/*`.

### Auth flow (frontend side)

1. **Login**: `Login.vue` POSTs `{ username, password }` to `/api/auth/login`. The backend sets an **HttpOnly cookie** (`aqua_token`) — JavaScript cannot read it, the browser sends it automatically on all subsequent requests.
2. **User info**: The response body contains `data.user` (name, role) which is stored in `sessionStorage.setItem('aqua_user', ...)` for UI display and route guard checks.
3. **Routing after login**: Based on `user.role` → `FARMER` to `/dashboard/farmer`, `REGULATOR` to `/dashboard/regulator`, `ADMIN` to `/dashboard/admin`.
4. **Logout**: `request.post('/auth/logout')` → clears `aqua_user` from sessionStorage → redirects to `/login`.

### HTTP client (`src/utils/request.ts`)

A pre-configured Axios instance with:
- `baseURL: '/api'`
- `withCredentials: true` (required for HttpOnly cookie)
- Response interceptor: `code !== 200` shows `ElMessage.error`, `code === 401` redirects to login

All API calls should import this instance (`import request from '@/utils/request'`) rather than using raw axios.

### Known inconsistencies to be aware of

- **Route guard vs cookie**: `router/index.ts` checks `sessionStorage.getItem('aqua_token')` but the token is now HttpOnly — JS can't read it. The guard relies on `aqua_user` being set as a proxy for "logged in".
- **`Regulator.vue`** imports raw `axios` directly instead of the configured `request` instance for the logout call.
- **`api/` directory** is empty. API calls are made inline in components rather than through a dedicated API layer.
- **3 role SVG icon components** in `components/icons/` remain from the scaffold, unused by current pages.
